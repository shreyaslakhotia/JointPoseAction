## Compatibility versus resource constraints

**SAM 3D:** checked-in `doc/setup.md:5–6` requires an NVIDIA GPU with at least 32 GB VRAM. The custom code does not implement working sharding; initialization accumulates models on default CUDA before wrapping. Additional MoGe/DINO copies, decoder grid tensors, model weights and activations all matter. The fixed mesh grid at resolution 256 includes 1 GiB cube indices plus ~389 MiB vertices before temporaries. Its non-Module state is not automatically moved by module `.to()`. Input/preprocessing resize of 518×518 does not shrink these constructor allocations. fp16/autocast does not turn int64 index grids into half-sized floating tensors. These are static allocation estimates, not measured GPU peaks.

**Backend support:** FlashAttention 2's main CUDA implementation targets Ampere/Ada/Hopper; Turing uses a separate implementation, and native bf16 support requires newer architectures. The local attention default is SDPA and YAML selects float16, so FlashAttention presence alone does not prove the active run hits unsupported kernels. Other sparse/rendering kernels and backend choices need bounded runtime checks after CUDA is visible. [Official backend documentation](https://github.com/Dao-AILab/flash-attention#nvidia-cuda-support).

**fyp-pose:** CPU imports of torch/OpenCV/NumPy succeed. The torch CUDA 13.0 build and actual Turing execution remain untested; torchvision/compiled operator compatibility was not inferred from metadata. No claim is made that a particular mismatch caused historical segmentation output or SAM 3D OOM.

**System RAM:** current capacity is adequate for small geometric diagnostics and sequential representative annotation parsing. The all-view renderer could launch 34 workers, each repeatedly loading tens/hundreds of MB JSONs and decoding video, causing avoidable RAM/I/O contention. No full batch was run.
